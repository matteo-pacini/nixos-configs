## LUKS Encryption

Each data disk (disk0, disk2–disk9) is encrypted with LUKS2:

| Parameter | Value |
|-----------|-------|
| Cipher | AES-XTS-plain64 |
| Key Size | 512-bit |
| Hash | SHA256 |
| PBKDF | Argon2id |
| Key Management | agenix (decrypted at boot) |

The `/etc/crypttab` maps LUKS UUIDs to agenix key files:

```
disk0   UUID=acc41b71-...   /run/agenix/nexus/disk0
disk2   UUID=5f612cb9-...   /run/agenix/nexus/disk2
...
```

**Configuration**: `hosts/Nexus/hardware-extra.nix`

## mergerfs Pool

The `/diskpool` mount combines all 9 data disks into a unified namespace:

| Option | Value | Description |
|--------|-------|-------------|
| `allow_other` | enabled | Allow non-root users to access |
| `category.create` | mfs | New files go to disk with **most free space** |
| `posix_acl` | true | Enable POSIX ACLs |
| `moveonenospc` | true | Fall over to another branch if a write hits ENOSPC mid-write |
| `minfreespace` | 300G | Hard floor — `mfs` will skip any branch with less than this free |

**Configuration**: `hosts/Nexus/hardware-extra.nix`

## SnapRAID Parity

SnapRAID provides snapshot-based parity protection:

| Setting | Value |
|---------|-------|
| Data disks | d0, d2–d9 → `/mnt/disk0`, `/mnt/disk2`–`/mnt/disk9` |
| Content files | `/mnt/diskX/snapraid.content` (one per active data disk) |
| Parity file | `/mnt/parity1/snapraid.parity` |
| 2-parity file | `/mnt/parity2/snapraid.2-parity` |
| Exclusions | `*.unrecoverable`, `/tmp/`, `/lost+found/` |
| Touch before sync | enabled |

With dual parity, SnapRAID can recover from up to **2 simultaneous data-disk failures**.

**Note**: The NixOS snapraid-sync timer is disabled (sync is triggered during the backup job); the snapraid-scrub timer remains enabled and runs weekly (Sun 06:00).

**Configuration**: `hosts/Nexus/snapraid.nix`

## Idle Spindown (hd-idle)

All 11 pool HDDs (9 data + 2 parity) spin down after **1800s** idle. hd-idle
has no NixOS module — only the package — so `hosts/Nexus/hd-idle.nix`
hand-rolls the systemd unit.

The disk set is enumerated at service start from `/sys/block/sd*` where
`queue/rotational == 1`, not hardcoded: pool disks get swapped, and the
physical serials appear nowhere in the repo (data disks are addressed by LUKS
mapper name, parity by filesystem UUID). Rotational selects exactly the 11
pool HDDs — the root SSD and its mdadm mirror are non-rotational and are
never touched. The global default is `-i 0` (never spin down anything not
explicitly listed), so a disk that fails enumeration fails safe.

### SAS and SATA are not interchangeable here

Every drive sits behind the same megaraid_sas HBA, so `lsblk` reports a blank
`TRAN` for all of them and cannot be used to tell them apart. The signal the
unit uses instead: **a SATA disk exposes a `/dev/disk/by-id/ata-*` alias, a
SAS disk does not.** SAS drives fall back to their `wwn-*` alias. Addressing
by-id is load-bearing — kernel names (`sda`…) reshuffle across reboots.

| | SATA (disk3–disk9, both parity) | SAS (disk0, disk2 — HGST He10) |
|---|---|---|
| hd-idle args | `-c ata` | `-c scsi -p 3` |
| Command issued | ATA `STANDBY IMMEDIATE` | SCSI `START STOP UNIT`, POWER CONDITION = 3 |
| Parked state | Standby | Standby power condition |
| Wake trigger | Any media access | Any media access |
| Wake mechanism | libata, implicit in the ATA spec | Drive firmware, per SBC |

`-p 3` is the critical part and is **not** hd-idle's default. The `-p` value
lands in the POWER CONDITION field of the `START STOP UNIT` CDB, and when it
is non-zero the START bit is ignored:

| `-p` | Meaning | Next read |
|---|---|---|
| 0 (hd-idle default) | START bit honoured → plain **STOP UNIT** | Logical unit is *stopped*, not merely idle. Returns NOT READY 04/02 until the host sends an explicit `START UNIT`. |
| 2 | IDLE power condition | Auto-resumes (heads unloaded, platters still spinning) |
| 3 | STANDBY power condition | Auto-resumes (motor stopped) |

The mechanical result of `0` and `3` is identical — motor off, same power
saved. What differs is readiness. A drive in a power condition is still
`READY` and transitions itself back to active when a command needing media
access arrives. A *stopped* logical unit is not ready and will refuse reads
indefinitely.

Linux does have a recovery path for the stopped case — `scsi_eh_try_stu()`
sends the `START UNIT` for you — but it is gated on `allow_restart`, which
megaraid_sas leaves at `0` for SAS end devices (it sets `1` only for SATA, via
the `is_ata` SAT workaround). So NOT READY became EIO.

> **Do not "fix" a stalled SAS drive by setting `allow_restart=1`.**
> Measured on this hardware: the read does succeed, but via the SCSI error
> handler — a 35s stall, `megasas_disable_intr_fusion` across the whole
> controller, and `OCR is requested due to IO timeout!!` twice, surviving only
> by winning a race against the controller reset. The root mdadm mirror is on
> the same HBA, so a lost race resets the controller underneath `/`.
> The sysfs path, if you need to read it, is
> `/sys/block/sdX/device/scsi_disk/*/allow_restart` — not `device/allow_restart`.

hd-idle's own man page states the trap outright: power condition 0 "works fine
for disks accessible via the SCSI layer (USB, IEEE1394, ...), but it will
\*NOT\* work as intended with real SCSI / SAS disks."

### Verification

`drive-status` (root-only, ships with the module) prints the non-waking spin
state of every pool HDD:

```bash
sudo drive-status
```

Tools for ad-hoc work: `nix-shell -p hdparm sdparm sg3_utils`

| Task | SATA | SAS |
|------|------|-----|
| Query state | `hdparm -C <by-id>` (non-waking) | see gap below |
| Park for testing | `hdparm -y <by-id>` | `sg_start --pc=3 <dev>` |

**Known gap:** there is no working SAS state probe. `drive-status` detects a
*stopped* logical unit by its NOT READY sense, which a `-p 3` standby does not
produce — the drive answers normally and reads as `active` with the motor
down. Mode page 0x1a reports configuration rather than current state, and
`sg_start` has no query mode. There is a `FIXME` on that branch in
`hd-idle.nix`. Until it is solved, infer from read latency: ~10s cold versus
~10ms warm.

### Incident: 2026-07-28

The initial hd-idle deployment passed `-c scsi` without `-p 3`, parking disk0
and disk2 with a plain STOP UNIT. Timeline: spindown 17:54, first ext4 errors
20:26, both journals aborted and both filesystems remounted `emergency_ro` at
00:06. It surfaced as Paperless HTTP 500s, because `PAPERLESS_MEDIA_ROOT`
lives on `/diskpool`.

**No data was lost.** ext4 aborted on *read* EIO, so it went read-only
defensively before any bad write could reach the disk — the fsck logs showed
nothing but journal replay and cosmetic extent-tree optimisations, and the
subsequent `snapraid diff` reported 0 removed and 0 relocated.

Recovery, should a branch ever go read-only again:

1. Stop every writer and unmount. Use the writer list in
   [Disk Failure Handbook § A2 Quiesce writers](disk-failure-handbook.md#a2-quiesce-writers);
   unmount the pool *before* the branches (`systemctl stop diskpool.mount`,
   then `systemctl stop mnt-diskN.mount`).
2. `fsck.ext4 -fy /dev/mapper/diskN` — `-f` is required, a journal replay
   alone is not enough once the journal has aborted. Both branches can run
   concurrently; they are different spindles. Exit 0/1/2 is fine, 4 or 8 means
   stop and read the log.
3. Remount and confirm `emergency_ro` is gone from `/proc/mounts` before
   restarting any service.
4. `snapraid status && snapraid diff` — **read the diff before syncing.** A
   sync rewrites parity to match the current disk state, so if fsck moved
   files to `lost+found` it would destroy the only copy that could restore
   them (`/lost+found/` is in the SnapRAID exclusions, so those files appear
   in the diff as plain deletions). Once the diff is clean:
   `snapraid touch && snapraid sync`.

### Companion: smartd

`hosts/Nexus/services/smartd.nix` sets `-n standby,q` so smartd's ~30-minute
attribute polls do not wake sleeping disks. The daily short self-test
(`-s S/../.././02`) still wakes them at 02:00, which falls inside the nightly
backup window and so costs nothing extra.
